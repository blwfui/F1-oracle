项目的骨架是可信的：**README 里绝大多数头条数字我都能原样复现**（见 §5）。数据不是编的，`src/semantics.py` 的完赛/退赛唯一定义、`make_context()` 的结构性防泄漏、预测器工厂强制重建这几处设计也确实成立。

缺点集中在三处：

1. **有三个问题会直接改变结论**：2026 赛季积分多发 1 分（已被官方 API 证伪）；主指标 `ρ_all` 与退赛率强相关（−0.565），使跨年比较失真；基线选得偏弱，使"提升"被放大约一倍。
2. **"可复现"只兑现了一半**：README 的每个数字都真实，但产出其中 5 组关键数字（t=4.88、逐圈 Δρ、前 10 口径、DNF 的 AUC、逐圈 61,884 样本）的脚本**不在仓库里**，只存在于被 gitignore 的工作记录中；且 README 有 5 处标注与实测不符（样本量 190/173、t=4.88、"7/8 年为正"、MAE 3.40、逐圈"10%–50%"区间）。
3. **所有超参都在同一批 173 场上选出来**，没有任何留出集。粗切分复核显示 `k` 与权重在前后半段都稳定（不是灾难性过拟合），但名义 p 值仍系统性偏乐观，README 对此零提及。
   **→ 已补留出集（H4），见 `docs/留出集验证.md`。复核结论与本节一致：不是灾难性过拟合
   （留出 Δρ 全为正），但样本内口径确实高估，README 的措辞需要跟着改。**

**如果只改三件事**：

1. **积分口径与官方对账**（H1 + M1）—— 2026 的所有结论目前建立在被污染的积分上。
2. **加时间切分**（H4）—— 例如 2018–2022 选参 / 2023–2025 评分，`k`、`α`、`gain`、融合权重全部改到留出集上选；否则所有"显著"都应标注为样本内。
   **→ 已做，见 `docs/留出集验证.md`。留出结论成立（赛前 +0.0314 / 前向滚动 +0.0354，均越门槛），
   但同一批 test 场上的样本内口径高估 0.003–0.009；且 `α`、`k` 在折间不稳定，不能被写成"调出来的最优值"。**
3. **让 `run_backtest.py` 打印年份区间与 n，并把 t 统一到实际生产配置**（M3）—— 赛前 5.25 / 赛后 4.94，而不是借来的 4.88。

## 1. A 组：影响结论正确性的问题

### H1【高】2026 赛季积分多发 1 分（最快圈 +1 分，规则 2025 年起已废止）【已实测】

**现象**：`ingest.py` 无条件给最快圈车手加 1 分，没有年份分支。

**证据**：`src/etl/ingest.py:225-227`

```python
pts = F1_POINTS.get(pos, 0) if pos else 0
if fastest_lap_driver and drv == fastest_lap_driver and pos and pos <= 10:
    pts += 1
```

**实测（与官方 API 逐车对账）**：2026 R1（官方 `https://api.jolpi.ca/ergast/f1/2026/1/results.json`）

| 车手 | 名次 | 官方 points | 库内 points |
|---|---:|---:|---:|
| RUS | 1 | 25 | 25 |
| … | | | |
| VER | 6 | **8** | **9** ← 官方 `FastestLap.rank=1`，但 2026 不再给分 |

- 该轮库内合计 **102**（标准前 10 = 101）。
- 每轮积分合计扫描：2026 **16/17 轮 ≠ 101**；2025 **17/17 轮 = 101**；2018 **21/21 = 101**（2018 尚无最快圈分）。
- 2026 赛季库内总分 **1733**。

**为什么 2025 看不出来**：`scripts/fetch_official.py:132-142` 会用官方 `points` 无条件覆盖 `results.points`，所以凡跑过官方对账的年份（2019–2025）错误都被掩盖；而该脚本默认 `YEAR = 2025`（`fetch_official.py:20`），**从未对 2026 执行**。也就是说这是一个被对账掩盖了七年、到第 9 季才暴露的系统性 bug。

**影响**：2026 车手积分榜、`views/01_赛季总览.py` 的累计积分曲线、`views/06_赛前预测.py:68-77`（`_asof_points`）的"赛前积分榜"基线特征全部偏高 —— 也就是 README 主打的 2026 结论所依赖的输入。

**修复方向**：把积分规则做成 `(year) → 规则` 的显式表（最快圈分 2019–2024 有效，2018 与 2025+ 无效），并统一"官方值为准、缺失才回退公式"；对 `results.points` 加断言：与官方不一致时 WARN 而非静默。

**验证方式**：逐轮比对官方 `points`；或直接检查"每轮总分 ≠ 101 的轮次列表"。

### H2【高】主指标 `ρ_all` 与退赛率强相关（−0.565）→ 所有跨年 ρ 比较（尤其 2026）被 DNF 率混杂【已实测】

**现象**：`score_round()` 的 `rho_all` 把未完赛者按 FastF1 的**分类名次**（13–22 的乱序值）计入，而预测器无法预知谁会退赛。

**证据**：`src/model/backtest.py:248-257`（`_ranks()`：漏掉的车手一律排在最后）、`:267-268`（`rho_all` 用 `race.truth[d].position`）。

**实测（2018–2025，发车格基线）**：逐场"退赛条目占比"与 `rho_all` 的相关系数 **−0.565**；按退赛率四分位分箱：

| 退赛率箱 | 场次 | ρ 均值 |
|---|---:|---:|
| ≤10% | 74 | **0.7371** |
| 10–15% | 39 | 0.5964 |
| 15–20% | 23 | 0.5447 |
| >20% | 37 | **0.4595** |

2026 的退赛率是 **20.9%**（78/374），正好落在最差那一箱。`docs/2026-新规年预测评估.md:73-75` 把这个差异解释为"赛道超车更难、比赛更接近巡航"——**没有证据支持，属于把相关当因果**。

> ⚠️ **复核更正（2026-10-15，另一会话）** —— 本条下半段的机制与结论方向写反了，数字属实但推论不成立。
>
> **机制写反了。** 原文写"退赛越多 → 被'白送分'的那一层越大 → **ρ 越高**"，但上面的分箱表本身就是**反的**：
> 退赛越多 ρ 越**低**（0.7371 → 0.4595）。机制是：`rho_all` 把未完赛者按**分类名次**（13–22 的乱序值）计入，
> 而预测器无法预知谁会退赛 —— 于是退赛越多，"不可预测的错位"越多，ρ 越低。

| 退赛率箱 | 场次 | ρ 均值 | 方向 |
|---|---:|---:|---|
| ≤10% | 74 | **0.7371** | ← 退赛最少，ρ 最高 |
| 10–15% | 39 | 0.5964 | |
| 15–20% | 23 | 0.5447 | |
| >20% | 37 | **0.4595** | ← 退赛最多，ρ 最低 |

> **推论也跟着反了。** 原文据此说 2026 的高 ρ"被混杂污染"。但混杂的方向是**压低** ρ，
> 所以 2026 在 20.9% 的高退赛率下仍拿到 0.6468，说明它的信号**比表面看起来更强**，而不是更弱。
>
> **按退赛率匹配的对照（本次复核实测）**：取历史退赛率 ≥20% 的场次（n=59，与 2026 同档）：
>
> | 组 | rho_all | rho_fin |
> |---|---:|---:|
> | 历史同档（n=59） | 0.4929 | 0.6996 |
> | **2026**（n=17） | **0.6468** | **0.8146** |
>
> 两个指标都远高于同退赛率组 → **2026 的高 ρ 不是退赛率混杂造成的**。
>
> **所以正确的动作是**：撤回"巡航化"的因果措辞（这一点原文对），但**保留甚至加强 2026 的数字**；
> 不要再写成"数字被污染"。复现命令：`python -m scripts.readme_numbers --full`。

**修复方向**：跨年比较仍应改用对退赛率不敏感的指标（`rho_fin`、MAE、前 N 集合重合），
或按退赛率分箱匹配后再比（本报告已给出匹配结果）；README 里的 2026 因果解读应撤回或标注为未证实。

**验证方式**：复算上述相关系数与分箱表；或按 2026 的退赛率对历史场次做加权匹配后重算 ρ。

### H3【高】基线偏弱：仓库里已写好更强的同复杂度基线却不进记分板，"提升"被放大约一倍【已实测】

**现象**：README 用"最笨基线"（赛前积分榜 0.5501 / 纯发车格 0.6204）作为对照，但这两个都不是现有信号集能达到的最强非 Elo 基线。

**证据**：`src/model/predictors.py:145-188` 实现了 `AvgFinishBaseline`（平均完赛名次，同样零拟合），但 `scripts/run_backtest.py:69-76` 的 `l0_predictors()` 里**没有它**。同类地，`predictors.py:224-269` 的练习赛/排位秒差基线单独看也不弱。

**实测（2018–2025，173 场）**：

| 对照 | 赛前 ρ | 赛后 ρ |
|---|---:|---:|
| README 使用的基线 | 积分榜 **0.5501** | 发车格 **0.6204** |
| 同复杂度但不含 Elo 的组合 | 积分榜+练习赛 **0.5768** | 发车格+秒差 **0.6355** |
| 库里已有、记分板未用的更强基线 | 平均名次(仅完赛) **0.5849** | — |
| `best_pre` / `best_post` | **0.6071** | **0.6543** |

于是：

- README 口径的增益：赛前 **+0.0570**、赛后 **+0.0339**
- 换成同复杂度对照：赛前 **+0.0303（t=4.75）**、赛后 **+0.0188（t=4.20）**
- 换成库里更强的"平均名次(仅完赛)"：赛前只剩 **+0.0222（约缩水 61%）**

更别扭的是：README 自己在 2026 那张表里用的正是 0.5768 这个"不含 Elo"的对照 —— 同一份文档对"提升"用了两把尺子。

**修复方向**：把 `AvgFinishBaseline(include_dnf=False)` 加进 `l0_predictors()` 重跑同一张表；对外表述统一为"相对同复杂度基线"的增益。

**验证方式**：`python scripts/run_backtest.py` 之后手工构造上述四个对照做配对检验。

### H4【高】全部结论在同一批 173 场上选型并评估：没有任何留出集或嵌套验证【已实测 + 代码审读】

**现象**：报告的每一个"显著增益"背后都有一个在**同一批数据**上取 argmax 的选择。

**调参面清单**（全部在 2018–2025 的 173 场上完成）：

| 自由度 | 位置 | 规模 |
|---|---|---|
| Elo `k` × `dnf_policy` | `scripts/run_backtest.py:423-433`（`--sweep`） | 9 × 2 = 18 组 |
| 融合权重 | `run_backtest.py:272-279` | 6 组 |
| 配对检验组合 | `run_backtest.py:287-317` | 7 组 |
| 罚退收缩 `α`、`min_pen` | `predictors.py:73-85` | 3 × 阈值（145 条罚退条目） |
| 逐圈 `gain` | `lappredict.py:19-25` | 4+ 档扫描，取内部峰值 0.25 |
| 逐圈 `window`、清洗阈值 ×5 | `lappredict.py:44`、`cleanlap.py:45-50` | "由全库实测确定" |

项目自己也知道这件事：`docs/prediction-projects-survey.md:71` 把"固定 train/val/test 时间切分 + 预注册阈值"评为最严格协议，`:139-141` 建议补"预注册 kill criterion" —— 但 `src/`、`scripts/` 里搜不到任何 `holdout` / `train_test_split` / `validation` 的生产路径。

**我做的粗切分复核（结论对项目有利，应一并记录）**：把 2018–2021 与 2022–2025 分半看，`k` 的排序稳定（192 在前半 0.5881 / 后半 0.6001，均为最优或并列最优），融合权重的最优点在两半一致（0.4/0.3/0.3 都在最优附近，邻域差距仅 0.002–0.003）。**所以这不是灾难性过拟合**，问题在于报告的 p 值没有扣除"从 18+ 组里挑最好"这件事，名义显著性偏乐观。

**修复方向**：按赛季做 leave-one-season-out 或"2018–2022 选参 / 2023–2025 评分"的嵌套验证；把 `--sweep` 的输出与最终选点一起留档。

**验证方式**：按年份留出重跑 `best_pre` / `best_post` 与基线，看留出年增益是否缩水。

**✅ 复核结果（2026-10-15，`scripts/holdout_eval.py`）**：修复方向里提的两件事都做了，而且做了三个协议。

每折在**看不见的年份**上重选全部超参 —— Elo `k`×`dnf_policy` 18 组 + 罚退收缩 `α`×`min_pen` 15 组 + 赛前/赛后融合权重各 21 组 = **75 组/折**。判据 `KILL` 预注册（`Δρ>0` 且 `t>2` 且 正向年份≥半数），**写在看到任何结果之前**，并有回归测试钉死（`tests/test_holdout.py`），事后放松判据会直接测试失败。

| 协议 | 赛前 Δρ（t） | 赛后 Δρ（t） | 裁决 |
|---|---|---|---|
| **1 主切分**：train 2018–2022 → test 2023–2025，n=70 | **+0.0314**（2.658） | +0.0169（**1.998**） | 赛前 ✅ / 赛后 ❌ 踩线 |
| **2 前向滚动**（唯一无泄漏，test 年只用它之前的赛季），n=114 | **+0.0354**（3.708） | **+0.0248**（3.729） | 两者 ✅ |
| **3 留一赛季**（训练含未来赛季，非前瞻），n=173 | +0.0315（5.402） | +0.0225（3.805） | 两者 ✅ |

对照一律是 README 的「同复杂度」口径。**本项目最好的证据是前向滚动那一条（n=114，两个口径都过门槛且 5/5 年为正）** —— 它没有任何时间上的泄漏。

**三件必须先看的事，否则会误读成"完美通过"：**

1. **乐观量是真的，只是小。** 同一批 test 场（2023–2025）上，样本内口径是 赛前 +0.0400 / 赛后 +0.0202，留出只有 +0.0314 / +0.0169 → **高估 0.0086 / 0.0033（21% / 16%）**。这正是本节指控的那部分，应当从 README 的名义增益里扣掉。
2. **`α` 和 `k` 根本没被"选"出来。** 各折的 argmax：`α` 取遍 {0.5, 0.75, 1}，`k` 在 {96, 192} 间跳。`best_post` 写的 `α=0.75, min_pen=3` **在留出调参里一次都没被选中** → 它不能被写成"调出来的最优值"，只能写成"一组效果相近的取值之一"（目标函数在这个方向上是扁的）。`dnf_policy=finishers_only` 则 8/8 折一致，**这条确实被数据识别出来了**。
3. **顺带修掉一个网格缺陷。** `min_pen` 初版网格 (3,5,10) 里**每一折都命中上边界 10** —— 边界命中意味着网格卡住了调参器，那样的"选点"没有意义。扩到 (3,5,10,15,20) 后落到 10/15，不再撞边界。

另外两点记录在案：赛后权重 `0.4+差0.2+Elo0.4` 在 **8/8 折完全一致**，但与 `best_post` 现用的 `0.4/0.3/0.3` 不同（说明"秒差权重再低一点、Elo 再高一点"更稳）；留一赛季协议的各折训练集重叠率达 84%，**其 t 值只能读作"一个配置在 173 场上的配对 t"，不是 8 次独立泛化检验**。

完整选点表与逐折明细：`docs/留出集验证.md`（`python -m scripts.holdout_eval --loso --write` 重新生成）。
