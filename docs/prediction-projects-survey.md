# GitHub F1 预测项目调研

> 调研日期：2026-10-13　方法：GitHub Search API 5 轮 + 逐项目读 README 原文 + 权威赛果核对
> 目的：确认外部同类项目「预测什么」与「报出多少准确率」，为 F1 Oracle 选择主指标提供依据

---

## 一、核心结论

**这些项目的准确率数字互相不可比。** 因为预测目标分四层，难度与基准率完全不同：

| 层 | 预测什么 | 候选集 | 单变量基准 |
|---|---------|--------|-----------|
| ① 冠军 | 20 选 1 | 20 | 49.1%（杆位夺冠） |
| ② 领奖台 | 前 3 | 20 | ≈ 86.7%（发车格基线前 3 命中） |
| ③ 是否拿分 | 二分类 | 2 | ≈ 50% |
| ④ 完整排序 | 20 人全排 | 20! | Spearman 0.622 |

「90.6% 准确率」与「Spearman 0.690」不是同一把尺子。对外比较前必须先问：**你预测的是哪一层。**

## 二、逐项目明细

### Tier 1 —— 值得对标

#### `deepan-alve/F1-model`

- **预测**：完整完赛排序（LightGBM learning-to-rank）+ 独立 DNF 分类器 + 赔率隐含概率特征
- **自报指标**：**Spearman 逐场，2026 赛季前 15 站均值 0.690**，前 3 命中均值 1.67/3
- **工程闭环（最值得抄的部分）**：GitHub Actions 双 cron —— 周六 23:00 UTC 排位赛后出预测，周一 12:00 UTC 用真实赛果打分并写 `data/results/{year}_{race}.json`，README 由 `scripts/update_readme.py` 自动重写。每场预测训练时**排除该场本身**。

> ⚠️ **2026-10-13 核查修订（原判「可信度高」不成立）**
> 把仓库 15 个 `data/results/2026_*.json` 全下下来自己重算，逐场 ρ 与仓库字段**差 0.0000**（数字没造假），
> 但**口径有结构性问题**：`actuals` 把所有退赛者统一赋成 `FinishPosition = 21.0`（并列同一名次）。
> 全季 330 条真值里 **172 条（52%）被并列**；平均每场只有 **10.5 / 22** 人有真实名次。
> 最极端：加拿大站 22 人中 18 人（82%）是并列 21.0，只有 4 人有真实名次。
>
> 控制实验：把并列的 21.0 随机拆成互不相同的名次（500 次 Monte Carlo 取均值）——
> | 口径 | ρ |
> |---|---|
> | 并列 21.0（= 仓库自报口径） | **0.6898** |
> | 打散成真实名次后 | **0.6115** |
> | 落差 | **−0.0783** |
>
> **打散后 0.6115 < F1 Oracle 的纯发车格基线 0.6204。** 落差与并列规模成正比：
> 并列 5–7 人的场次只掉 0.004~0.016，并列 14–18 人的场次掉 0.09~0.18。
>
> 用 F1 Oracle 口径重算他的冠军类指标：
> | 指标 | deepan 2026（15 站） | F1 Oracle 2018–2025 |
> |---|---|---|
> | 猜中冠军 | **46.7%**（7/15） | 52.0%（发车格基线） |
> | 冠军落在预测前 3 | 86.7%（13/15） | 86.7%（发车格基线） |
> | 冠军平均预测名次 | 2.07 | 2.29 → 2.07（融合模型） |
> | 领奖台命中 | 55.6%（25/45） | — |
> | MAE | 4.64（含退赛）/ 2.46（仅完赛者） | 3.40~3.51 |
>
> **他的猜中冠军 46.7% 低于杆位基线 49.1%。**
>
> 另两个时效性问题：① **前 4 站是批量回填** —— 澳/中/日/迈阿密四场的文件生成时间同为
> 2026-05-05 12:50–12:51，而澳大利亚站实际在 3 月，不是赛前发布的预测；
> ② **流水线已停** —— `last_processed.json` 停在 R15（2026-09-27），
> `upcoming_prediction.json` 是空占位符（`predictions: []`），仓库最后 push 为 2026-09-28。
>
> **结论**：不必视为被超越。但他的**工程闭环**（自动出预测 → 自动打分 → 自动重写 README）
> F1 Oracle 完全没有，这是最该抄的一项。

#### `akakarantzas/chicane-ai`
- **预测**：两两「谁排在谁前面」（H2H 成对分类）
- **指标**：2026 测试集（15 站）race-macro accuracy **70.11%**、Brier 0.1966、log loss 0.5809；训练集 4,183 对 / 23 场，验证集 4,374 对 / 24 场
- **验证方式**：本项目见到**最严格的协议** —— 固定 train(2024)/val(2025)/test(2026) 时间切分、预注册阈值、哈希留证、镜像样本、只允许按验证集选型
- **可信度**：最高。且**诚实报告自己的学习模型没能击败启发式**：逻辑回归 Brier 增益 0.001039 < 预设阈值 0.002，梯度提升增益 0.000269 且降低了覆盖率 → 最终保留启发式，未部署

## 三、案例核对：`frankndungu/f1-shanghai-prediction-2025`

这是唯一一个把预测**公开发布、可被验证**的项目。它预测 2025 上海站：

| 预测 | 实际（F1 官方赛果） | 结果 |
|---|---|---|
| P1 Verstappen | P1 **Piastri** | ✗ 冠军错 |
| P2 **Lawson** | Lawson 实际 **P12** | ✗ 差 10 位 |
| P3 Russell | P3 Russell | ✓ |

前 3 命中 1/3。实际前三为 Piastri → Norris → Russell（迈凯伦包揽冠亚）。
另：Leclerc / Hamilton / Gasly 因技术违规被取消资格，Alonso 因刹车故障退赛。

**值得记的一点**：该项目 README 自称「Sophisticated method for handling 2025 driver lineup changes」，
但它把 Lawson 排到 P2 —— 显然是拿 2024 年 Lawson 在 RB 车队的表现 + 红牛车队强度做的推断。
**车手换队处理是这个领域的系统性弱点**，也正是 F1 Oracle 用「车手 Elo + 车队 Elo 分开建模」要解决的问题。

## 四、对 F1 Oracle 的四条结论

1. **主指标用 Spearman 是对的**，且这是唯一有可比对象的指标 —— `deepan-alve/F1-model` 报的是同一口径。对外的数字应与它对照，而不是与「90.6%」对照。

2. **已复核：`deepan-alve/F1-model` 的 0.690 站不住。** 我已把它的 15 个原始 JSON 全部重算 ——
   逐场 ρ 与他自报**完全一致**（差 0.0000），但他对退赛者采用「全部并列 21.0」的赋值，
   全季 52% 的真值是并列的。控制实验（打散并列）显示真实水平约 **0.6115**，
   **低于我们的发车格基线 0.6204**；猜中冠军 46.7% 也低于杆位基线 49.1%。
   → 结论：**目前没有外部项目在同等口径下超过 F1 Oracle。**

3. **但要抄他的工程闭环。** 他做成了我们没有的一件事：GitHub Actions 每周自动出预测 →
   自动用真实赛果打分 → 自动重写 README 战绩表。F1 Oracle 已有 `run_backtest.py` 与
   `data/f1_oracle.db`，缺的只是「定时跑 + 把结果写回一个可展示的地方」。

4. **`chicane-ai` 的做法值得借鉴**：预注册阈值 + 诚实报告「模型没打赢基线」。
   F1 Oracle 的 `run_backtest.py` 已经做了配对 t 检验，可以再补一层「预注册 kill criterion」——
   把「提升不到 +0.03 就停」写成代码里的断言，而不是写在文档里。

## 五、方法论收获：查任何外部 ρ 之前，先查真值里的并列结构

本次核查最有价值的一条经验。**退赛者如果被并列赋成同一个名次，Spearman 会被系统性抬高**，
抬升幅度约等于并列群体占总体的比例 —— 因为模型不必为「谁会退赛」这个纯随机事件排序，
而真实名次赋值会强制它排。

量化证据（同为 15 场，仅改退赛者的赋值方式）：

| 并列规模 | 场次数 | ρ 平均落差 |
|---|---|---|
| 5–7 人并列 | 6 场 | −0.004 ~ −0.016 |
| 10–12 人并列 | 2 场 | −0.06 ~ −0.09 |
| 14–18 人并列 | 7 场 | −0.09 ~ −0.18 |

F1 Oracle 的 `results.position` **给退赛者互不相同的分类名次（11–20，均值 18.4）**，
恰好避开了这个问题 —— 所以我们的 0.6204 比他的 0.6898 更「实」。
这条要写进对外比较的检查清单：**先问「退赛者怎么赋名次」，再比 ρ。**
